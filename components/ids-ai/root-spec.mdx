## Color System

All component styling must use semantic tokens (`var(--...)`), not hardcoded color values.
Semantic color tokens resolve to different values in **Light** vs **Dark** themes. **Primitive** palette tokens are static across themes (foundation values referenced by semantic tokens or rare direct use in specs).

### IDS-AI baseline: canonical names vs Figma `codeSyntax` exports

**Applies to:** All IDS-AI component design specs under `components/ids-ai/**/design-spec.mdx` (Button, Alert, Checkbox, Masthead, etc.). Token tables and codegen contracts in those files MUST use **canonical** semantic CSS names (the vocabulary this root-spec and Figma semantics agree on—not ad hoc numbered names unless you are documenting the raw Figma export in **Metadata / Source mapping** only).

**Design specs** use **canonical semantic CSS names** (for example `--color-background-alerting-info`, `--color-icon-alerting-success`). The Figma → `components/ids-ai-theme.css` sync may emit **only numbered or split exports** (for example `--color-background-alerting-info-1`) and omit the bare canonical variable.

**Policy:** `components/ids-ai-theme.css` is the single place that closes that gap for the whole design system. After each variable sync, the build injects **semantic alias lines** in the default (light) selector block so canonical names resolve with `var(--…-1)` (or the appropriate export) when Figma did not define the bare name. Dark mode continues to override the underlying numbered tokens; aliases are not duplicated in the dark block because they reference `var()` of those tokens. The authoritative list of alias pairs lives in `scripts/sync_ids_ai_theme_from_figma.py` (`_ids_ai_semantic_alias_declarations`). **Do not** treat scattered per-component CSS fallbacks as the primary baseline fix—extend the theme aliases when new canonical names are missing from exports.

**Per-component specs:** Do not copy this alias policy into every `design-spec.mdx`. For one-off clarifications (e.g. a component that first exposed a gap), you may add a one-line pointer: “Canonical tokens; IDS-AI theme semantic aliases per `components/ids-ai/root-spec.mdx`.” Optional `var(--canonical, var(--numbered))` in implementation is only for **legacy IDS** (`ids-theme.css`) compatibility, not the primary IDS-AI contract.

The **Core semantic** tables below are a curated shortcut; the authoritative Light/Dark matrix is the **Color Mode** section (synced from Figma collection `41837:5099`) and `components/ids-ai-theme.css`. Primitive palette tables align with the IDS-AI file `Primitive` collection (`GET /v1/files/rr8F0NGA6RNY9Z0cNeh3jh/variables/local`).

### Icon Resolution Baseline (Framework-Agnostic)

Use this contract for every IDS component spec and for any framework target that consumes IDS design tokens.

- When a component requires an icon, generators must **first** look for an existing framework or library `Icon` component in the target codebase.
- Generators must **inspect** that `Icon` component’s public API and bind the design-spec icon using the **real** shape or name input prop (for example `name`, `icon`, `shape`, or `glyph`) rather than assuming a fixed prop key.
- Icon lookup must prefer **canonical** icon names from the component `design-spec.mdx` first, then any **declared fallback** icon names in that same spec.
- Raw SVG or image fallback is allowed **only** when no compatible icon component or named icon asset is available in the target project.

**Asset path baseline (when specs reference files, not only names):** resolve icons from `assets/icons/<slug>.svg` unless the component spec documents a different stable slug-to-path mapping.

## Icon primitive (codegen — framework-agnostic)

Monochrome glyphs MUST be rendered through a single design-system **icon primitive** (component name and import path are **implementation details** chosen by the target app and codegen config). The **contract** below is normative for IDS-AI specs; it does not reference Storybook, React, or any demo app.

| Concept | Contract |
|---|---|
| **Asset slug** | Maps one-to-one to a file **`{slug}.svg`** in the design system’s agreed icon bundle (IDS-AI: under the repo’s `assets/icons/` tree unless a spec overrides the bundle root in **Source mapping**). Slug pattern: lowercase letters, digits, hyphens (e.g. `shield-encrypt-alt`, `grid-square-9-16`). |
| **`shapeName` (logical)** | The slug string passed to the icon primitive so it resolves the correct SVG asset. |
| **`color` (logical)** | Optional semantic **CSS color** for the glyph, expressed as `var(--…)` from token tables in this root-spec or the component spec. **Omit** when the **parent interactive host** already sets `color` and state transitions must drive the glyph via inheritance (e.g. `currentColor` on press/active). |
| **`variant` (logical)** | **Monochrome:** `mask` (CSS mask + `currentColor`) vs **`inline`** (inline `<svg>` from asset, still token-colored via `currentColor` in artwork) when the implementation maintains an allowlist for bundle control. **Fixed palette:** `img` or equivalent for severity / multi-color artwork. Specs say which applies; prop names may differ by framework. |
| **Generators** | Resolve the concrete module/class for the active design system + target framework from **tooling config** (e.g. design-system YAML), not from `design-spec.mdx`. Emit the logical `shapeName`, `color`, and `variant` per spec; do not hand-roll low-level mask markup when the project’s icon primitive is available. |

**Repository tooling (non-normative):** In SDD-IDS, optional mappings for codegen (e.g. React import path) live under `config/design_systems/ids-ai.yaml` (`codegen` keys). They are **not** part of the Figma design contract.
